**Evidence:** src/client/controllers/CombatController/Hitbox.lua:24 resolves the target with `hit_part:FindFirstAncestorOfClass("Model")` and :33-36 drops the hit if that Model has no Humanoid. src/server/services/WeaponAttachment.lua Attach clones the weapon Model and parents it straight into the character (`clone.Parent = character`), and prepare() (:17-45) only sets CanCollide=false, leaving CanQuery on. ## 2. [do-now] Stop answering spam Attack packets 1:1 and put every remote behind one per-player budget (effort S, impact medium)

**Evidence:** src/server/services/CombatService.lua:252-261: a malformed attack_index is rejected before _allow_remote runs (:253-256), and a rate-limited request is also answered with _reject_attack (:258-260). Each inbound Attack packet therefore produces one FireClient no matter the rate. Correction to the raw idea: moving the rate check first does NOT remove the amplifier. The always-reply rule is deliberate (comment at :249-251, from the recent fix). Rate limiting exists in two different shapes: CombatService:_allow_remote (:123-139, per-action min interval) and InventoryService:_allow_remote (InventoryService.lua:120-130, a single interval). Neither allows bursts, neither has a global budget, and neither counts drops. Hit packets have no throttle at all (:22-31). A target that fails validation is never added to HitTargets (:412), so the same target can be resubmitted until MAX_HIT_REQUESTS_PER_ATTACK=32 (:20), each time re-running up to 8 raycasts (CombatValidation.lua:9, :48-68).

**Why:** Each new remote (abilities, emotes, trading) copies one of the two limiter shapes or leaves one out. An exploiter can spread spam across N remotes, and today every Attack packet costs a reliable server send.

**Proposal:** Immediate fix: for malformed or rate-limited Attack requests, send at most one AttackRejected per window. The client's PendingAttackTimeout (CombatConfig) already covers a silent drop. Count rejected targets in `active.Rejected[target]`, stop validating a target after 2 failures in one attack, and lower MAX_HIT_REQUESTS_PER_ATTACK to about MAX_HITS_PER_ATTACK+4. Structural fix: add server/network/RemoteBudget.lua, a token bucket with `budget:Take(player, action) -> boolean`, configured as `{ global = {rate=60, burst=120}, actions = { ["Combat.Attack"] = {rate=12, burst=3}, ... } }`. State lives on the PlayerSession, and dropped packets are reported to Telemetry. Both services call it, and their RemoteAt tables are deleted. This is the first concrete piece of the deferred typed network layer.

## 17. [before-scale] Lag-compensate hit validation with a shared server position history and arm early HitStarts instead of dropping them (effort M, impact high)

**Evidence:** CombatValidation.lua:141 (reach), :147 (distance_to_bounding_box vs HitPositionTolerance) and :152 compare client-observed geometry with server state at packet arrival. HitPositionTolerance is 3 (Katana.lua:56), while SprintSpeed is 24 (shared/movement/Config.lua) and vaults move about 32 studs/s, so roughly 125-150ms of interpolation plus ping puts a sprinting victim past tolerance. An early HitStart is discarded (CombatService.lua:364-366), and the client fires it once (AttackLifecycle.lua:50), so a jitter compression between the Attack and HitStart packets loses the whole swing. MovementValidation already samples every root each Heartbeat (MovementValidation.lua:205, trims with table.remove(samples,1) at :286), but only for its own use.

**Why:** Parkour makes fights between moving targets the norm, and more players means more mobile and high-ping players. False rejects grow with speed x ping, and the usual reaction of raising tolerance per weapon weakens the anti-cheat for everyone. Heavier weapons with later HitStartAt values are more exposed to the early-drop path.

**Proposal:** Add server/services/PositionHistory.lua: a per-character ring buffer (64 entries of {t, rootCFrame, boxCFrame, boxSize}, written once per Heartbeat) with `Sample(character, t)` interpolation. MovementValidation reads from it instead of keeping its own Samples. In ValidateHit, `rewind = clamp(attacker:GetNetworkPing() + 0.1, 0, 0.3)`, and test the target's box and reach at now - rewind while using the attacker at now, then tighten tolerance to about 1.5-2. Store an early HitStart as PendingHitStart and activate it at HitStartOpensAt. Telemetry reason codes (above) measure the before and after. Add CombatValidation.spec cases with synthetic histories.

## 18. [before-scale] Item model plus versioned, session-locked persistence before items carry value (effort L, impact high)

**Evidence:** Inventory is memory-only and seeded from `TEMPORARY_SLOTS = { [2] = "Katana" }` on every join (InventoryService.lua:17-19, :132-149). _player_removing drops it (:151-154). Slots store bare weapon-id strings (:279), so two Katanas are indistinguishable, and SelectItem picks the first match (:324-328). Fists is a fake slot-less item special-cased in GetSelectedId (:226-234), Has (:237), SetSlot (:260) and SelectItem (:315). The wire format is `{Slot, WeaponId}` (:43-46, PlayerController.lua:31-35). There is no DataStoreService use anywhere in src.

**Why:** The first save will lock in `{[2]="Katana"}`-shaped data. Adding consumables, skins or duplicate weapons later then means a migration of live profiles and a protocol change at the same time. Without session locking, server hops can duplicate items.

**Proposal:** Add shared/items/ItemCatalog.lua (`ItemId -> { Kind = "Weapon", WeaponId, Stackable }`). A server slot becomes `{ Uid = GenerateGUID, ItemId, Data = {} }`, the wire becomes `{Slot, Uid, ItemId}`, and selection is by Uid. The default weapon becomes `Inventory.DefaultWeaponId` config used by WeaponService when the slot is empty, so the inventory never contains Fists. Add server/services/PlayerDataService.lua wrapping ProfileStore (session lock, autosave, BindToClose, kick on load failure), with the schema in shared/data/Schema.lua (`{ Version = 1, Inventory = { Slots = { ["1"] = {...} } } }`, string keys, a Migrations table). It runs as the first lifecycle component and sets session.Phase to Ready, and InventoryService builds from session data. TEMPORARY_SLOTS becomes the Studio default profile.

## 19. [before-scale] Session-scoped client owners for each remote (CombatClient, LoadoutClient) (effort M, impact medium)

**Evidence:** The Combat remote's OnClientEvent is connected inside the per-character CombatController (CombatController/init.lua:63-92), so HitConfirmed, AttackAccepted or AttackRejected arriving between CharacterRemoving and the next controller are dropped. Hitmarker reaches into `character_controller.CombatController` and rebinds on every respawn (UIController/Hitmarker.lua:53-67). Equipped-weapon state is held in PlayerController.CurrentWeaponId (:55, :99), WeaponController.Equipped and the AnimationController weapon, and PlayerController pushes it into each by hand (:99-103). PlayerController.lua:88-91 states the single-listener rule as an unwritten convention.

**Why:** Every new HUD element (health, stamina, combo, kill feed, cooldowns) and every new server-to-client message (damage taken, status effects, round state) needs a home. Per-character listeners lose messages during respawn, and more copies of equipped state means more desync bugs like the ones the recent UI fix addressed.

**Proposal:** Add client/session/CombatClient.lua as the only Combat listener, with signals AttackAck, AttackRejected and HitConfirmed, plus the future victim and FX messages. Add client/session/LoadoutClient.lua as the only Weapon and Inventory listener, holding EquippedId, Entries and SelectedSlot with EquippedChanged and InventoryChanged signals. Payload validation (is_valid_inventory, PlayerController.lua:23-40) moves there. The per-character CombatController subscribes to CombatClient through its Trove. UI receives the session clients once at construction, and CharacterController reads `loadout.EquippedId` and subscribes to its changes. This is the client half of the deferred typed network layer.

## 20. [later] Stop re-cloning the weapon model on every selection toggle (effort S, impact low)

**Evidence:** Each selection change goes InventoryService:_sync -> Changed (InventoryService.lua:190-200) -> WeaponService:Equip, which calls _character_added (WeaponService.lua:242) to destroy the character trove and clone the model again (:110-124, :171; WeaponAttachment Attach `source:Clone()` plus welds and tag_hitpoints). SelectSlot toggles back to nil when the same slot is selected again (InventoryService.lua:300-302), so mashing at the 0.08s limit (:16) swaps Fists and Katana about 12 times a second. Equip warns on every call when a template is missing (WeaponService.lua:222-228), and a client can trigger that path.

**Why:** Heavier weapon models (meshes, VFX, trails) times 30 players means replication churn for everyone and server log spam under abuse.

**Proposal:** Cache attached models per character in WeaponService: `{[weaponId] = {model, motors}}`, built lazily, owned by the character trove (or the session component), and swapped by parenting to a per-player holder instead of destroy and clone. Coalesce equips to the latest request per 0.2s using task.defer and a dirty flag. Warn about a missing template once per weapon id per server.

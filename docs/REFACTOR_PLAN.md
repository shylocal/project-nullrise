# Refactor plan (design contract)

This document is the authoritative design for the `refactor/scale-foundations` work. Agents implement exactly what is written here. It will later be renamed to `docs/ARCHITECTURE.md` by the FINISH agent.

Review items are referenced as **R1–R20**, the numbering of the ranked review (`review-ideas.md`). The user's 18-item summary maps 1:1 onto R1–R18; R19 (session clients) and R20 (weapon model caching) are also in scope.

---

## 0. Ground rules for every agent

- **Gate:** `sh scripts/analyze.sh`. Files you own must end with zero diagnostics (errors and lint warnings); you must not add diagnostics anywhere else. Once `selene.toml` exists (Phase 2), the same script also runs selene.
- **Baseline diagnostics** (present before this work) are assigned in §11 to the agent that owns the file.
- **New modules** start with `--!strict` and must be clean under it. Existing modules get `--!strict` in Phase 3; a Phase 1/2 agent may add it early to a file it rewrites, but only if the file is clean.
- **House style:** tabs; `snake_case` locals and module-private functions; `PascalCase` public methods, fields, module tables and signals; `Trove` for cleanup; `Signal` (packages.Signal) for events; comments describe invariants, not history.
- **No silent config fallbacks** (`x or 0.15`). Config is validated at load (§3.1). Constructor dependencies are **required** and checked with `Deps.check` (§3.9); there are no defaulted deps.
- **No infinite `WaitForChild` in specs.** Index Rojo-synced instances directly (`ServerScriptService.server.services.X`) or use `FindFirstChild` and `assert`. Every spec you own that currently uses `WaitForChild` must be fixed.
- **Git:** only INTEGRATE / FINISH agents run `git add`/`commit`. Nobody else stashes, resets, checks out or branches.
- **Ownership:** edit only the files the §11 table assigns to you in your phase. Anything else goes into `NEEDS_OUTSIDE` in your report.
- **Deviations:** do not edit this file concurrently. Report each deviation in your final report; the phase's INTEGRATE agent records it in §16.
- **Feel:** Fists and Katana keep identical damage, timing, ranges, cooldowns and movement speeds. Every intentional behaviour change is listed in §14, and nothing outside that list may change.
- **No CI.** It was removed on purpose in #93. Do not re-add it.

### 3.1 `shared/config` (P1-shared)

`require(ReplicatedStorage.shared.config)` returns a deep-frozen table:

```lua
export type Config = {
	Movement: MovementConfig, Parkour: ParkourConfig, Combat: CombatConfig,
	Inventory: InventoryConfig, World: WorldConfig, Network: NetworkConfig,
	Data: DataConfig, Telemetry: TelemetryConfig,
	validate: (sections: any) -> { string },   -- pure; used by specs with broken copies
}
```

`init.lua` requires each section, validates every section with `Schema` (§3.3; unknown keys are errors), collects **all** errors, raises one error `"Invalid config:\n<errors>"` (level 0) if any, then `Freeze.deep`s the result. The section files return plain tables.

**Movement.lua**
```lua

```

**Parkour.lua:** every key currently in `ParkourController/Config.lua` with identical values, **except** `ClimbableTag` and `ClimbableCollisionGroup`, which move to World. Add:
`CornerProbeMissTtl = 0.2, FrameRayBudget = 48, BudgetWarnInterval = 5`.
Validation: all numbers finite and `>= 0`; `VaultEnabled` is a boolean; `VaultDurationMultiplier` is in [0.5, 1.5]; `CornerProbeRecheckDistance < CornerLockDistance`; `MaxTopSurfaceHits` and `FrameRayBudget` are positive integers.

**Envelope.lua** (pure, not part of the frozen tree):
```lua
export type MotionSource = { Horizontal: number?, Upward: number? }
export type Limits = { MaxHorizontalSpeed: number, MaxUpwardSpeed: number, MaxDownwardSpeed: number,
                       TeleportDistance: number, Sources: { [string]: MotionSource } }
Envelope.compute(movement: MovementConfig, parkour: ParkourConfig, gravity: number): Limits
```
Sources (M = Movement, P = Parkour):
```
Walk      H = M.WalkSpeed
Sprint    H = M.SprintSpeed
Vault     H = (M.SprintSpeed + P.VaultForwardBoostSpeed) / P.VaultDurationMultiplier
VaultExit H = M.SprintSpeed + P.VaultForwardBoostSpeed
TopHop    H = M.SprintSpeed + P.VaultTopHopForwardBoostSpeed
          U = sqrt(2 * gravity * (P.VaultMaxHeight + P.VaultTopHopHeightMargin))
Traverse  H = P.TraverseSpeed * P.TraverseSprintMultiplier
Mantle    H = P.MantleMaxInward / P.MantleDuration
          U = (P.MantleMaxRise + P.HangDrop) / P.MantleDuration
Jump      U = M.MaxJumpVelocity
MaxHorizontalSpeed = M.Envelope.HorizontalMargin * max(H)   -- 2.6 * 37.89 = 98.5 (was 96)
MaxUpwardSpeed     = M.Envelope.UpwardMargin * max(U)       -- 4.8 * 50 = 240 (unchanged)
MaxDownwardSpeed / TeleportDistance copied from M.Envelope.
```
`Envelope.spec` (P1-shared) asserts that every source fits inside the computed limits, and that changing a source (for example doubling SprintSpeed) raises the limit.

### 3.3 `shared/utility/Schema.lua` (P1-shared)

Declarative checks that collect every error and reject unknown keys.
```lua
export type Spec = { kind: string, [string]: any }  -- opaque
Schema.number(opts: { gt: number?, gte: number?, lt: number?, lte: number?, integer: boolean? }?): Spec
Schema.string(opts: { nonEmpty: boolean?, pattern: string?, maxLength: number? }?): Spec
Schema.boolean(): Spec
Schema.enum(values: { string }): Spec
Schema.enumItem(enum: Enum): Spec               -- typeof EnumItem and EnumType == enum
Schema.optional(spec: Spec): Spec
Schema.record(fields: { [string]: Spec }, opts: { open: boolean? }?): Spec
Schema.map(key: Spec, value: Spec, opts: { nonEmpty: boolean? }?): Spec
Schema.array(item: Spec, opts: { minLength: number? }?): Spec   -- must be dense 1..n
Schema.custom(check: (value: any, path: string) -> string?): Spec
Schema.check(value: any, spec: Spec, path: string): { string }
```
Error strings are `"<path>: <message>"`. Paths look like `Katana.Attacks[2].HitWindow` and `Movement.Envelope.HorizontalMargin`. The messages are exactly these: `must be a number`, `must be finite`, `must be > X`, `must be >= X`, `must be < X`, `must be <= X`, `must be an integer`, `must be a string`, `must not be empty`, `must match X`, `must be at most N characters`, `must be a boolean`, `must be one of: a, b`, `must be an Enum.X`, `is required`, `unknown key`, `must be a table`, `must be a dense array`, `must have at least N entries`.

### 3.4 `shared/weapons` (P1-shared, Phase 1 shape = current Attacks/Charge)

**Types.lua** (`--!strict`, exports only):
```lua
export type AnimationDef = { Id: string, Priority: Enum.AnimationPriority, Looped: boolean,
                             TransitionTime: number?, SharedWith: string? }
export type AttackDef = { Animation: AnimationDef, Hitbox: string, Damage: number, Cooldown: number,
                          MinDuration: number, HitStartAt: number, HitWindow: number,
                          HitPositionTolerance: number, Range: number, CanSprintWhileAttacking: boolean? }
export type ChargeDef = AttackDef & { HoldTime: number, MaxHoldTime: number }
export type WeaponDefinition = { Id: string, Type: "Melee", Model: string, CanSprintWhileAttacking: boolean,
                                 Wield: { [string]: string },
                                 Animations: { Equip: AnimationDef, Idle: AnimationDef, Sprint: AnimationDef, Charge: AnimationDef? },
                                 Attacks: { AttackDef }, Charge: ChargeDef? }
```
P2-combat replaces these types in Phase 2 (§9.1).

**Validator.lua**
```lua
Validator.KINDS: { [string]: Schema.Spec }       -- { Melee = MELEE_SPEC }
Validator.check(definition: any, id: string): { string }   -- schema, then cross-field rules; all errors
Validator.validate(definition: any, id: string?): (boolean, string?)  -- compat: errors joined by "\n"
```
- An unknown or misspelled `Type` gives the error `"<id>.Type: must be one of: Melee"`, and nothing else is checked for that definition.
- `AttackDefaults` (optional, a partial attack record) is shallow-merged into each attack and into `Charge` **before** schema checks. Authored keys win.
- `Charge` is optional. `Animations.Charge` is required if and only if `Charge` exists.
- Cross-field rules: `Cooldown >= MinDuration` on every attack and on the charge; `Charge.MaxHoldTime > Charge.HitStartAt`; animation roles that share an `Id` must declare `SharedWith = <other role>` on the later role (Equip < Idle < Sprint < Charge order).
- `validate_combat_config` is deleted (config validation lives in `config/init.lua`).

**Fists.lua / Katana.lua:** remove `MeleeType` (never read) and add `SharedWith = "Idle"` to `Katana.Animations.Sprint`. Every number stays identical.

**Loadouts.lua:** `return { Starter = { [2] = "Katana" } }`. Catalog validates that each value is an equippable id and not `DefaultId`, and that each key is an integer in `1..Config.Inventory.MaxSlots`.

**Catalog.lua**
```lua
Catalog.DefaultId: string                         -- "Fists", declared next to WEAPON_IDS
Catalog.Ids(): { string }                         -- frozen, WEAPON_IDS order
Catalog.All(): { WeaponDefinition }               -- frozen, same order
Catalog.Get(id: any): WeaponDefinition?
Catalog.Has(id: any): boolean
Catalog.IsEquippable(definition: any): boolean    -- a Catalog definition whose Type is in Validator.KINDS
Catalog.Loadout(name: string): { [number]: string }  -- frozen; errors on unknown name
```

## 4. Server architecture (Phase 1, P1-server)

### 4.1 PlayerSession
```lua
export type Phase = "Loading" | "Ready" | "Leaving"
PlayerSession.new(player: Player): PlayerSession
session.Player: Player
session.UserId: number
session.Phase: Phase                 -- written only by PlayerService
session.Character: Model?
session.Trove: Trove                 -- destroyed with the session
session.CharacterTrove: Trove?       -- new per character; destroyed when that character is removed
session.CharacterAdded: Signal (character)
session.CharacterRemoving: Signal (character)
session:Set(key: any, state: any): ()   -- replaces; a previous state with :Destroy() is destroyed
session:Get(key: any): any
session:Clear(key: any): ()             -- destroys state if it has :Destroy()
session:Destroy(): ()                   -- removes character, clears all state, destroys Trove
```
**Do not use `Trove:AttachToInstance(character)`.** The character can still be unparented at `CharacterAdded`, and Trove 1.8 errors in that case. Instead, connect `character.Destroying` to remove the character.

### 4.2 PlayerService and components
```lua
export type Component = {
	OnPlayerAdded: ((self: any, session: PlayerSession) -> ())?,       -- may yield
	OnCharacterAdded: ((self: any, session: PlayerSession, character: Model, trove: Trove) -> ())?,
	OnCharacterRemoving: ((self: any, session: PlayerSession, character: Model) -> ())?,
	OnPlayerRemoving: ((self: any, session: PlayerSession) -> ())?,
}
PlayerService.new(deps: { players: Players, telemetry: Telemetry })
svc:Register(component: Component, name: string): ()   -- before Start only; order = registration order
svc:Start(): ()                                        -- connects Players events, then processes existing players once
svc:Get(player: Player): PlayerSession?                -- any phase
svc:GetReady(player: Player): PlayerSession?           -- Phase == "Ready" only
svc:GetPlayers(): { Player }                           -- deps.players:GetPlayers()
svc.PlayerAdded: Signal (player, session)              -- fired when the session is created (Loading)
svc.PlayerReady: Signal (player, session)
svc.PlayerRemoving: Signal (player, session)           -- fired before component teardown
svc:Destroy()                                          -- runs leave for every session
```
**Join** (`task.spawn` per player; ignore if `player.Parent ~= deps.players` or a session already exists):
1. Create the session (Phase `Loading`) and fire `PlayerAdded`.
2. For each component in order: `pcall(component.OnPlayerAdded, component, session)`. On error, warn `"[PlayerService] <name>.OnPlayerAdded failed for <player>: <err>"` and call `telemetry:Count(player, "Lifecycle", "ComponentFailed", name)`, then continue. Record each component whose hook returned. After each hook, if `session.Phase == "Leaving"`, stop.
3. Set Phase `Ready` and fire `PlayerReady`. If `session.Character` is set, dispatch `OnCharacterAdded` to each component in order.
4. Character events: dispatch `OnCharacterAdded` / `OnCharacterRemoving` (pcall each) only while `Ready`. `OnCharacterAdded` runs in registration order and `OnCharacterRemoving` in reverse. The `trove` argument is `session.CharacterTrove`.

**Leave** (Players.PlayerRemoving or Destroy):
1. Set Phase `Leaving` and fire `PlayerRemoving`.
2. If the session was Ready and has a character, call `OnCharacterRemoving` in reverse order.
3. Call `OnPlayerRemoving` in reverse order, only for components whose `OnPlayerAdded` completed. A component whose `OnPlayerAdded` is still yielding must notice `Phase == "Leaving"` itself when it resumes.
4. Then `session:Destroy()` and remove it from `Sessions`.

Remote handlers act only on `GetReady(player)` sessions. The `RemoteBudget` is the exception: it counts any session.

### 4.4 RemoteBudget (`server/network/RemoteBudget.lua`)
```lua
export type Rate = { Rate: number, Burst: number }
export type BudgetConfig = { Global: Rate, Actions: { [string]: Rate } }
RemoteBudget.new(deps: { players: PlayerService, config: BudgetConfig, clock: () -> number, telemetry: Telemetry })
budget:Take(player: Player, action: string): boolean
```
- `Take` refills both buckets `min(Burst, tokens + Rate * dt)`. It returns true only if both the action bucket and the global bucket have at least 1 token, and then consumes one from each.
- An unknown action consumes one global token if available, returns false, and calls `telemetry:Count(player, "Network", "UnknownAction", action)`.
- A denied take calls `telemetry:Count(player, "Network", "RateLimited", action)`.
- No session means it returns false.
- The bucket state is a session component state, `session:Set(budget, state)`. It is created in `OnPlayerAdded` and dies with the session. It does **not** reset on respawn.

Action keys are `"<Remote>.<Action>"`, for example `"Combat.Attack"`. Budgets come from `Config.Network.RemoteBudget`.

### 4.5 Telemetry (`server/services/Telemetry.lua`)
```lua
export type Category = "Combat" | "Movement" | "Network" | "Lifecycle" | "Data"
Telemetry.new(deps: { config: TelemetryConfig, scheduler: Scheduler, analytics: AnalyticsLike?, is_studio: boolean })
	-- analytics: { LogCustomEvent: (self, player: Player, name: string, value: number?, fields: {[string]: string}?) -> () }
telemetry:Count(player: Player?, category: Category, reason: string, detail: string?): ()
	-- detail = weapon id for Combat, action for Network
telemetry:GetSuspicion(player: Player): number
	-- per-player value v <- v * 0.5^(dt / HalfLife) + weight(reason), evaluated lazily
telemetry:Snapshot(): { [string]: number }    -- "<category>.<reason>.<detail or '-'>" -> count since last flush
telemetry:Flush(): ()
telemetry:Forget(player: Player): ()
telemetry:Destroy(): ()
```
- `Start()` schedules `Flush` every `FlushInterval` using `scheduler.after`, rescheduled on each flush.
- `Flush` sends one `LogCustomEvent(player, "Reject_<Category>", count, { CustomField01 = reason, CustomField02 = detail or "-" })` per (player, category, reason, detail) with a nonzero count. Each call is wrapped in pcall.
- In Studio, `Flush` also prints one line `[Telemetry] <category>.<reason>.<detail>=n ...` if anything was counted.
- Telemetry is not a PlayerService component, because PlayerService depends on it. `PlayerService` calls `telemetry:Forget(player)` after leave.

### 4.6 CombatService (Phase 1 changes)
```lua

-- RemoteLike = { OnServerEvent: SignalLike, FireClient: (self, player: Player, ...any) -> () }
```

### 5.6 CharacterState (P1-parkour owns; P1-client consumes)
`client/controllers/CharacterState/init.lua`:
```lua
export type Activity = "Attack" | "AttackRooted" | "Hang" | "Mantle" | "Vault" | "TopHop" | "Stunned"
export type Action = "Attack" | "Charge" | "Sprint" | "Vault" | "Grab"

state:Acquire(owner: any, activity: Activity): Lease   -- several leases per activity allowed
state:CanStart(action: Action): (boolean, Activity?)    -- false + first blocking active activity

lease:Release(): ()   -- idempotent
state:Destroy(): ()   -- releases all leases, destroys all overrides (restoring base values)
```
`Policy.lua` maps each activity to the actions it blocks. It is client-side, because only client controllers consult it (a deliberate deviation from R9's "shared config" wording).
```lua
Attack = {}, AttackRooted = { "Sprint" },

Mantle = { "Attack", "Charge", "Sprint", "Vault", "Grab" },
```

- **CombatController:** `Attack` and `Charge` return early unless `state:CanStart(...)`. A started attack acquires `Attack`, or `AttackRooted` when `can_sprint_while_attacking` is false. The lease is released where `SetSprintBlocked(false, self)` is called today.
- **ParkourController:** `try_vault` checks `CanStart("Vault")` and `_grab` checks `CanStart("Grab")`. Parkour states hold `Hang`, `Mantle`, `Vault` and `TopHop` leases.
- **MovementController:** `sprinting = Sprint held and moving and state:CanStart("Sprint")`. It re-evaluates on `state.Changed`. `SetSprintBlocked` and `SprintBlockers` are deleted.

`HumanoidOverrides.lua`:
```lua

HumanoidOverrides.new(humanoid: Humanoid): HumanoidOverrides
o:Push(owner: string, props: { [Property]: any }): Handle

handle:Pop(): ()                                -- idempotent
o:Base(property: Property): any                 -- value captured when its stack was empty; current value if none
o:Destroy(): ()                                 -- pops everything
```
- Each property has its own stack, and the effective value is the most recent live handle's value.
- The base value is captured when the first handle for that property is pushed. It is written back when the stack becomes empty, but only if `humanoid.Parent ~= nil`.
- `JumpingEnabled` maps to `Get/SetStateEnabled(Enum.HumanoidStateType.Jumping)`.

### 5.10 Dependency interface types (Phase 3)

Client classes take their collaborators as structural `*Like` types rather than as the concrete class types. A `*Like` type lists only the fields and methods the consumer reads, and its methods take `self: any`, so the real class (a metatable-backed type) and a plain-table spec fake both satisfy it. The checker does not match metatable classes against table types otherwise.

| Type | Defined in | Shape | Used by |
| --- | --- | --- | --- |
| `InputLike` | `InputController`; narrower copies in `MovementController`, `ParkourController/Types` and `CombatController/Types` | `ActionBegan`, `ActionEnded`, `IsDown(action)` (CombatController needs only the two signals) | MovementController, ParkourController, CombatController |
| `MovementLike` | `ParkourController/Types` | `IsSprinting()` | ParkourController |
| `CombatLike` | `CombatController/Types` | the session CombatClient: `AttackAccepted`, `AttackRejected`, `Send(action, ...)` | CombatController, CharacterController and PlayerController deps |
| `AnimationLike` | `CombatController/Types` | `Combat` (`CombatLayerLike`: `BeginMove`, `Play`, `Pause`, `Resume`) and `StopAction()` | CombatController |
| `CharacterLike` | `PlayerController` | `CharacterController`, or `{ Character, Destroy }` | PlayerController's `create_character` factory |
| `AnimatorLike` | `AnimationController/TrackCache` | the `LoadAnimation` surface of an `Animator` | `TrackCache.new(animator: Animator \| AnimatorLike)` |

Every client module types its troves with `ClientTrove.Trove` (`src/client/ClientTrove.lua`), a non-generic view of Trove 1.8. `typeof(Trove.new())` carries generic methods that do not unify across modules, so two modules' class types then compare unequal. Server modules keep troves as `any` (`PlayerSession.Trove`). `AnimationController/Types` and `CombatController/Types` hold the class interface types that the controller's submodules share, with one constructor `:: any` each.

## 9. Phase 2 designs

### 9.1 Weapon schema v2 and moves (P2-combat; R7, R8)
```lua
export type MoveKind = "Light" | "Charge"
export type HoldDef = { HoldTime: number, MaxHoldTime: number }
export type MoveDef = { Name: string, Id: number, Kind: MoveKind, Animation: AnimationDef, Hitbox: string,
                        Damage: number, Cooldown: number, MinDuration: number, HitStartAt: number, HitWindow: number,
                        HitPositionTolerance: number, Range: number, CanSprintWhileAttacking: boolean?, Hold: HoldDef? }
export type WeaponDefinition = { Id: string, Type: "Melee", Model: string, CanSprintWhileAttacking: boolean,
                                 Wield: { [string]: string },
                                 Animations: { Equip: AnimationDef, Idle: AnimationDef, Sprint: AnimationDef },
                                 MoveDefaults: { [string]: any }?, Moves: { [string]: MoveDef },
                                 Combo: { string }, Bindings: { Primary: { Tap: string, Hold: string? } } }
```
**Rules:**
- `MoveDefaults` is shallow-merged into each move before the schema runs.
- Move names match `^%a[%w_]*$`. `Name` and `Id` are injected by the Catalog and forbidden in authored data.
- `Hold` is required if and only if `Kind == "Charge"`.
- `Combo` lists one or more names of `Light` moves.
- `Bindings.Primary.Tap` is `"Combo"` or a move name.
- `Bindings.Primary.Hold` is an optional name of a `Charge` move.
- Every move must be reachable from `Combo` or `Bindings`.
- `Cooldown >= MinDuration`, and `Hold.MaxHoldTime > HitStartAt`.

**Catalog additions:**
```lua
Catalog.GetMove(weapon_id: string, move_id: any): MoveDef?
Catalog.MoveId(weapon_id: string, name: string): number?
Catalog.ComboMoveId(weapon: WeaponDefinition, index: number): number
```
Move ids are assigned per weapon by sorting move names with `<` and numbering from 1, so Fists gets Heavy=1, Light1=2, Light2=3.

**1:1 conversion.** Both weapons use `Bindings = { Primary = { Tap = "Combo", Hold = "Heavy" } }` and `Combo = { "Light1", "Light2" }`. The Heavy animation is the old `Animations.Charge`, and `Animations.Charge` is removed.

| Weapon | Move | Hitbox | Dmg | Cooldown | MinDur | HitStartAt | HitWindow | Tol | Range | Hold |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| Fists | Light1 | RightFist | 10 | 0.3 | 0.3 | 0.1 | 0.55 | 3 | 8 | – |
| Fists | Light2 | LeftFist | 10 | 0.3 | 0.3 | 0.1 | 0.55 | 3 | 8 | – |
| Fists | Heavy (Charge) | RightFist | 20 | 0.6 | 0.6 | 0.15 | 0.55 | 3 | 8 | 0.15 / 10 |
| Katana | Light1, Light2 | Mesh | 15 | 0.35 | 0.35 | 0.1 | 0.55 | 3 | 10 | – |
| Katana | Heavy (Charge) | Mesh | 30 | 0.6 | 0.6 | 0.15 | 0.55 | 3 | 10 | 0.15 / 10 |

Animation ids, priorities, `Looped` and transition times are copied verbatim. A golden-value spec asserts every number in this table.

**Server (`MoveKinds.lua`)**
```lua
export type Timing = { HitStartOpensAt: number, HitStartClosesAt: number, ExpiresAt: number }
MoveKinds[kind] = {
	create_timing: (move: MoveDef, started_at: number, tolerance: number) -> Timing,
	hit_expires_at: (move: MoveDef, active: any, now: number, tolerance: number) -> number,
}
```
`Light` and `Charge` use exactly the current formulas from `_create_active` and `_hit_start`.

CombatService keeps one `Active` record and a combo cursor (`ComboIndex`). An `Attack(move_id)` is handled as follows:
- If it is the combo-expected move, it is accepted and the cursor advances.
- If it is any other move bound in `Bindings` (for example Heavy), it is accepted without touching the cursor.
- Otherwise it is rejected.

Accepted moves always get one reply, and non-combo moves now get a reply too. Migration order inside P2-combat: first the internal rename (AttackKey to MoveId, with Charge mapped), keeping the specs green; then the data change and protocol swap in the same agent run.

**Client.** The client sends `Attack(move_id)` for both tap and hold. Only combo moves set `PendingAttack`. Every `== "Charge"` comparison becomes `move.Kind == "Charge"`. `AnimationController/Combat.lua` loads tracks with role `"Move:" .. move.Name`.

**Hitbox reuse.** The Hitbox is created once per equip and wielded part, and only started and stopped per HitStart and HitStop. It is destroyed on weapon swap or character teardown. This is the R1 follow-up.

### 9.2 DamageService (P2-combat; R16)
```lua
export type Combatant = { Model: Model, Player: Player? }
export type DamageRequest = { Source: Combatant, Target: Model, Amount: number, Kind: "Melee",
                              WeaponId: string, MoveId: number, Position: Vector3 }
export type Policy = (request: DamageRequest, amount: number) -> (number, string?)  -- new amount, block reason
DamageService.new(deps: { players: PlayerService, scheduler: Scheduler, config: CombatDamageConfig, tags: WorldTags })
svc:AddPolicy(name: string, policy: Policy): ()      -- ordered; duplicate name errors
svc:IsDamageable(model: Model): (boolean, Humanoid?)
	-- alive humanoid via CharacterQuery, AND (player character OR Damageable tag OR AllowUntaggedHumanoidTargets)
```

- **Built-in policies**, registered in the constructor in this order:

  2. `SpawnProtection`: a target player's character younger than `SpawnProtectionSeconds` (0 disables it) gives 0.
  3. `Team`: when `FriendlyFire` is false, both players are non-neutral and on the same Team gives 0.

- When an amount is reduced to 0, the reason returned is the policy name; Telemetry counts `Blocked`.

- **`CombatFxService`:** `.new(deps: { damage, players, remote: UnreliableRemoteLike, config: { RelevanceRadius } })`. On `Damaged` it fires `CombatFx` "Hit" to the victim player (always) and to every player whose character root is within `RelevanceRadius` of `Position`.
- **Client:** `CombatClient` gains `FxHit: Signal(victim, source, weapon_id, move_id, position, amount)` and `Damaged: Signal(amount, source)`, which fires when the victim is the local character.
- **UI modules:**
  - `UIController/HitHighlight.lua` adds a pooled `Highlight` on the victim for 0.12s, with no template needed.
  - `UIController/DamageIndicator.lua` uses an optional `ScreenGui` template `DamageIndicator` containing a `GuiObject` named `Flash`. It shows the flash for 0.15s on `Damaged`.

### 9.3 Lag compensation and PendingHitStart (P2-combat; R17)
```lua
export type Sample = { Time: number, RootCFrame: CFrame, BoxCFrame: CFrame, BoxSize: Vector3 }
PositionHistory.new(deps: { players: PlayerService, scheduler: Scheduler, step: SignalLike, capacity: number })
history:Sample(character: Model, t: number): Sample?   -- interpolated; clamped to the oldest and newest samples
history:Latest(character: Model): Sample?
history.Stepped: Signal (now: number)                  -- fired after each step's writes
```
- PositionHistory is a component: it tracks characters in `OnCharacterAdded` and untracks them in `OnCharacterRemoving`.
- Each step writes a ring buffer entry per tracked live character.
- **ValidateHit:** gains a final param `opts: { History: PositionHistory?, Rewind: number }`.
  - CombatService computes `Rewind = clamp(attacker:GetNetworkPing() + LagCompensation.InterpolationDelay, 0, MaxRewind)`.
  - The checks run against the current state first.
  - If the result is `Reach` or `OffBody`, and history has the target, the reach and box checks are retried using the target sample at `now - Rewind`. The attacker uses its current position, and LOS runs to the rewound root.
  - A success via rewind counts `Combat/Rewound`. This only makes validation more lenient.
  - `HitPositionTolerance` stays at 3; tightening it is a later data change gated on telemetry.
- **MovementValidation:** subscribes to `history.Stepped` instead of Heartbeat. It reads `history:Latest(character)` and keeps only its own derived window `{Position, Time, FallStartY}`.
- **PendingHitStart:** an early HitStart stores `active.PendingHitStart = true` and schedules `after(HitStartOpensAt - now, activate)`. `activate` re-checks that the attack is still current, the attacker is valid and the wielded part has not changed, then activates exactly as an on-time HitStart would, using `now = HitStartOpensAt`.

## 14. Intentional behaviour changes (exhaustive)

1. Hits on an enemy's weapon geometry now resolve to the enemy (R1). Weapon parts are `CanQuery = false`, so casts pass through them to the body.
2. Attack requests that are malformed or budget-dropped get at most one `AttackRejected` per 0.25s, instead of one per packet. Hit packets are budgeted at 60/s with a burst of 16. Attack, HitStart and inventory requests allow small bursts. Server `MinDuration` still governs gameplay.
3. Charge (Heavy) requests now receive `AttackAccepted`/`AttackRejected` (Phase 2).
4. Attack and Charge cannot start while Hanging, Mantling or Vaulting (R9).
5. The movement observer's horizontal limit moves from 96 to 98.5 studs/s (derived). The upward limit is unchanged.
6. PC hotkeys 3–9 select slots 3–9.
7. The corner fan is cached for 0.2s while traversal is blocked.
8. Early HitStarts are armed instead of dropped. Validation is lag-compensated, and the union rule only makes it more lenient (Phase 2).
9. Hit FX are new: a highlight on the victim for nearby players, and a damage flash for the victim if its template exists (Phase 2).
10. Inventory persists across sessions. Studio uses the mock store by default (Phase 2).
11. Damage policies (Invulnerable attribute, spawn protection = 0, friendly fire off) are no-ops with today's content. Untagged Humanoid models stay valid targets through `AllowUntaggedHumanoidTargets = true`.
12. Remote budget state is not reset on respawn (previously `RemoteAt` was).
13. Hanging on a MeshPart, WedgePart or UnionOperation climb guide and pressing A/D no longer errors every frame (Phase 3). The cylinder check in `Traversal.traverse` now uses `IsA("Part")` instead of `IsA("BasePart")`, because only a `Part` has a `Shape`. Cylinder guides behave as before.
14. Hit packets that arrive while an early HitStart is armed (before `HitStartOpensAt`) are buffered and validated when the window opens, instead of being dropped as `NotActive` (Phase 3). The client reports each target once per swing, so such a target could not land for the rest of the swing before.
15. (Finish, client) A Climbable Model guide moved by PivotTo, a tween or its PrimaryPart is re-measured on the next query, and a Model that contains an unanchored BasePart is measured live on every query, as before the refactor. Each query costs two property reads per static Model guide (`GetPivot` and one reference part's CFrame). Review finding 8.
16. (Finish, client) When the Animator is replaced mid-attack, the attack finishes at once: HitStop is sent, the hitbox stops and the attack lease is released. Before, they stayed open until the next attack or Reset. `AnimationController.CacheReset` carries this. Review finding 9.
17. (Finish, client) After a window focus loss, the first Left Shift press sprints again. Before, it was swallowed. Adapters may define an optional `ReleaseAll()`, which InputController calls on focus loss. Review finding 10.
18. (Finish, server) After a Charge (Heavy) is held past its HitStart marker and released, the next Hold-bound move's hit window cannot open before `release + Hold.HoldTime + HitStartAt - TimingTolerance`. An earlier HitStart is armed until then. Legitimate play cannot reach this bound, because a new hold needs a fresh press after the release. Attack acceptance, Lights and cooldowns are unchanged. Review finding 1.
19. (Finish, server) Load-time sanitising no longer deletes saved records only because this build doesn't recognise them, such as an unknown ItemId or a slot above MaxSlots. They stay in the profile, are not replicated, equip the default weapon and keep their slot occupied. `Schema.sanitize(data)` lost its `max_slots` parameter and drops only structurally corrupt slots. A profile that is refused (newer, missing or invalid Version, or a failed migration) is now released exactly as saved, and a failure after the session starts releases the profile instead of leaking it. Review findings 2–4.
20. (Finish, server) UnknownAction telemetry no longer carries the client's action name: the detail is `<Remote>.<unknown>`, and Studio prints the raw name. Client events fired at the server-to-client `Weapon` and `CombatFx` remotes are drained and charged to the sender's budget. Review findings 5–6.
19. (User decision 1, client) A ledge grab can start during a light attack or a Heavy charge, and the grab cancels that attack: HitStop is sent, the hitbox and the move animation stop, the attack lease is released, and a pending tap, buffered hold or held charge is dropped. Before, the attack kept playing while hanging. CombatController reacts to `CharacterState.Changed` reporting Hang active. Hang still blocks new attacks; the cooldown and the server combo sequence are kept.

## 15. Risks

- **Concurrent contracts:** Phase 1 agents may finish before a contract module exists. The mitigation is the contract-first rule in §12, with INTEGRATE-1 reconciling anything left over.
- **License:** ProfileStore is **Apache-2.0**, not MIT as the task brief assumed. Its notice must ship in `licenses/`, and VENDORED.md must say so.
- **Trove 1.8 `AttachToInstance`** semantics (§9.8). Also, Trove cleanup order is not guaranteed, so ordered teardown uses Runtime.
- **Rojo merging** of `$path` with explicit children is assumed. P2-content verifies it with `rojo sourcemap` before deleting anything, and the fallback is documented.
- **Envelope:** `Workspace.Gravity` is read at service construction. A runtime gravity change does not update the limits (documented).
- **`GetNetworkPing`** semantics and Studio's zero ping: rewind then uses only `InterpolationDelay`.
- **Analyzer gaps:** luau-lsp may lack definitions for `RaycastParams:AddToFilter` or `AnalyticsService` custom field enums. Agents use string field names and `:: any` at that boundary, with a comment.
- **Tests run only in Studio.** Every rewritten spec is checked by inspection and by the analyzer only. The INTEGRATE agents must list the manual smoke tests in `docs/TESTING.md` that cover each behaviour change in §14.
- **Parkour parity:** the state, overrides and latch rewrite is the riskiest change. The lifecycle specs must keep every existing assertion (renamed fields only).

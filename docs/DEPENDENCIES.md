# Runtime dependencies

Third-party packages come from Wally (`wally.toml`, installed into the git-ignored `Packages/` and `DevPackages/`) or are vendored under `src/packages` and `src/server/vendor`; see [VENDORED.md](VENDORED.md) for their sources and licenses. Run `~/.rokit/bin/wally install` (or `sh scripts/analyze.sh`, which runs it when needed) before building with Rojo. The authored UI and weapon-model contents remain Studio-only by design and are not expected to be generated by Rojo; both are verified against the weapon Catalog at boot (see below).

## ReplicatedStorage.packages

| Module | Source | Used by | Purpose |
| --- | --- | --- | --- |
| `Trove` | Wally `sleitnick/trove@1.8.0` (`Packages/`) | controllers, services, tests | Resource/lifecycle ownership |
| `Signal` | vendored `src/packages/Signal.lua` | controllers and services | In-process events |
| `ShapecastHitbox` | vendored `src/packages/ShapecastHitbox/` | client combat | Weapon hitbox sampling |

`default.project.json` maps each module by name (plus Wally's `_Index`), so they replicate to every client and require paths do not depend on where a package comes from.

`TestEZ` (Wally dev dependency `roblox/testez@0.4.1`) is only needed for `tests/` and is therefore not in `ReplicatedStorage.packages`: Rojo maps `DevPackages/TestEZ.lua` to `TestService.TestEZ`, beside the specs.

`ProfileStore` is vendored server-only at `src/server/vendor/ProfileStore.lua` (`ServerScriptService.server.vendor`).

## ReplicatedStorage.ui

Client code expects Studio-authored `ScreenGui` templates. Each is optional: a missing template disables only that UI module, without affecting gameplay. `Hitmarker` and `WeaponMenu` log one warning when missing; `DamageIndicator` is silent. Templates are cloned once per session into `PlayerGui` with `ResetOnSpawn = false`.

- `WeaponMenu`: a GUI template containing `GuiButton` descendants with a string `WeaponId` attribute. A descendant named `Selection` should be a `GuiObject` used as the selected-state indicator.
- `Hitmarker`: a GUI template containing a descendant named `Hitmarker` that is a `GuiObject`.
- `DamageIndicator`: a GUI template containing a `GuiObject` named `Flash`, shown for 0.15s when the local character takes damage.

The hit highlight on victims (`HitHighlight`) needs no template.

These assets intentionally remain Studio-only and are not part of the Rojo source tree.

**Boot check (`src/client/UiContracts.lua`):** when the client starts, every `GuiButton` in the `WeaponMenu` template that has a `WeaponId` attribute must name a Catalog weapon id. A missing template is not an error. In Studio a mismatch stops the client script with every problem listed; live clients warn and continue.

## ServerStorage.weapon_models

Weapon templates are Studio-authored and intentionally server-only. `WeaponService` reads them from `ServerStorage.weapon_models` and clones the selected model into the player's character.

Required built-in templates:

Each template is a `BasePart`, or a `Model` containing at least one `BasePart`, named after the definition's `Model` field. `WeaponAttachment` then, for every entry in the definition's `Wield` table, finds the template descendant with that name (it must be a `BasePart`) and welds it with a `Motor6D` to the named R6 body part. Each move's `Hitbox` names the part combat hit validation uses; it must also be a `BasePart` (it is looked up as a wield entry first, then anywhere in the template). Every `Attachment` named `Hitpoint` inside the template is tagged `Hitpoint` on attach, and hits are only accepted from such an attachment inside the move's hitbox part.

- `Fists`: `BasePart` descendants named `RightFist` (welded to `Right Arm`) and `LeftFist` (welded to `Left Arm`). These are also the hitboxes; each needs at least one `Attachment` named `Hitpoint`.
- `Katana`: a `BasePart` descendant named **`Handle`**, welded to `Right Arm`. Without it the Studio boot stops at the AssetContracts check below; on a live server the katana would be cloned into the character without being welded to the arm, and `WeaponAttachment` warns about the missing wield part. The hitbox is a `BasePart` descendant named `Mesh` (for example the blade `MeshPart`) containing `Attachment`s named `Hitpoint`. `Mesh` must be welded to `Handle` (for example with a `WeldConstraint` authored in the template) so it moves with the arm.

Each template must match the weapon definition in `src/shared/weapons/*.lua`. Weapon parts are made `CanCollide = false` and `CanQuery = false` on attach, so hit casts pass through a held weapon to the body behind it. `WeaponService` keeps one cloned model per weapon per character and re-parents it on re-equip.

**Boot check (`src/server/AssetContracts.lua`, run first by `compose/Content.lua`):** before any service is built, the server verifies that:

- `ServerStorage.weapon_models` exists;
- every Catalog weapon has a template named after its `Model` that is a `BasePart` or a `Model` containing one;
- every `Wield` key resolves (recursive `FindFirstChild`) to a `BasePart`;
- every move `Hitbox` resolves to a `BasePart` that has at least one descendant `Attachment` named `Hitpoint`;
- every hitbox is a wield part, or is connected to one inside the template through `WeldConstraint`, `RigidConstraint` or joint (`Weld`, `Motor6D`, ...) `Part0`/`Part1` links, so it follows the arm.

In Studio any violation stops the server boot with every problem listed (`Server: failed to start AssetContracts: ...`); live servers warn each problem and keep running. `RuntimeContracts.spec` runs the same check per weapon.

Keeping templates in `ServerStorage` prevents clients from reading the source models before they are attached to a character.

## Animation manifest

`src/shared/weapons/AnimationManifest.lua` holds baked animation data (length and `HitStart`/`HitStop` marker times per animation id). When the Catalog loads, `AnimationContracts` checks every move whose animation has an entry: `HitStartAt` is at most the `HitStart` marker (+1 ms), a Light move's `HitStartAt + HitWindow` reaches the `HitStop` marker, `MinDuration` fits in the animation length, and a Charge move's animation has a `HitStart` marker. Ids without an entry are not checked, so an empty manifest checks nothing. **The manifest is still empty**: bake it once in Studio. Note that the Katana light moves now have a 0.6s `MinDuration`, which must not exceed the length of their animations.

To (re)bake it after changing animations or move timing:

1. Open the place in Studio with Rojo synced, in Edit mode (not a play test).
2. Open View > Command Bar and run `require(game.TestService.tools.BakeAnimationManifest).Run()`.
3. The tool loads every distinct Catalog animation through `KeyframeSequenceProvider`, prints the generated module source to Output and writes it to `ServerStorage.AnimationManifest_Generated`. Animations that fail to load are skipped with a warning and stay unchecked.
4. Copy that ModuleScript's whole source over `src/shared/weapons/AnimationManifest.lua` (Rojo does not sync Studio edits back), commit it, and delete `ServerStorage.AnimationManifest_Generated`.
5. Run the TestEZ suite. A timing mismatch makes the Catalog fail to load with the offending move listed (for example `Katana.Moves.Light1.HitWindow: ...`); fix the move data or the animation.

## World contract

The server registers the `Climbable` collision group during startup.

Climbable surfaces (grab, hang, ledge traversal, corners) **require the `Climbable` CollectionService tag**, on the part or on an ancestor (for example the model). The tag is what makes a surface a climb guide; tagged guides may be invisible, non-collidable query volumes.

The `Climbable` collision group alone does **not** make a part climbable. Parkour queries treat untagged parts in that group as helper geometry and ignore them, and vaults ignore both tagged parts and that group.

## Character contract

The project requires R6. **Set Game Settings > Avatar > Avatar Type to R6 in Studio**; this is a place setting that Rojo cannot set.

Weapon definitions and animations use R6 body-part names (`Right Arm` and `Left Arm`). On any other rig, `CharacterController` rejects the character (the client warns and skips character setup), and the server's `WeaponService` refuses to attach weapons (`WeaponAttachment.IsSupportedRig`) and warns. Without an attached weapon, `CombatService` rejects that player's attacks.

## Source/runtime boundary

Rojo can build the code and package tree directly from this repository once `wally install` has populated `Packages/` and `DevPackages/`. UI and weapon models are deliberate Studio-side authoring contracts rather than missing source dependencies.

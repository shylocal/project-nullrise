# Runtime dependencies

The repository vendors its third-party packages under `src/packages` (runtime) and `tests/TestEZ` (tests only); see [VENDORED.md](VENDORED.md) for their sources and licenses. The authored UI and weapon-model contents remain Studio-only by design and are not expected to be generated by Rojo.

## ReplicatedStorage.packages

The project currently vendors:

| Module | Used by | Purpose |
| --- | --- | --- |
| `Trove` | controllers, services, tests | Resource/lifecycle ownership |
| `Signal` | controllers and services | In-process events |
| `ShapecastHitbox` | client combat | Weapon hitbox sampling |

These package sources are mapped into `ReplicatedStorage.packages` from `src/packages` by `default.project.json`, so they replicate to every client.

`TestEZ` is only needed for `tests/` and is therefore not in `ReplicatedStorage.packages`: it lives in `tests/TestEZ`, which Rojo maps to `TestService.TestEZ`.

## ReplicatedStorage.ui

Client code expects Studio-authored `ScreenGui` templates. Each is optional: a missing template logs one warning and that UI module does nothing, without affecting gameplay. Templates are cloned with `ResetOnSpawn = false`.

- `WeaponMenu`: a GUI template containing `GuiButton` descendants with a string `WeaponId` attribute. A descendant named `Selection` should be a `GuiObject` used as the selected-state indicator.
- `Hitmarker`: a GUI template containing a descendant named `Hitmarker` that is a `GuiObject`.

These assets intentionally remain Studio-only and are not part of the Rojo source tree.

## ServerStorage.weapon_models

Weapon templates are Studio-authored and intentionally server-only. `WeaponService` reads them from `ServerStorage.weapon_models` and clones the selected model into the player's character.

Required built-in templates:

Each template is a `BasePart`, or a `Model` containing at least one `BasePart`, named after the definition's `Model` field. `WeaponAttachment` then, for every entry in the definition's `Wield` table, finds the template descendant with that name (it must be a `BasePart`) and welds it with a `Motor6D` to the named R6 body part. The definition's `Hitbox` names the part combat hit validation uses; it must also be a `BasePart` (it is looked up as a wield entry first, then anywhere in the template). Every `Attachment` named `Hitpoint` inside the template is tagged `Hitpoint` on attach, and hits are only accepted from such an attachment inside the attack's hitbox part.

- `Fists`: `BasePart` descendants named `RightFist` (welded to `Right Arm`) and `LeftFist` (welded to `Left Arm`). These are also the hitboxes; each needs at least one `Attachment` named `Hitpoint`.
- `Katana`: a `BasePart` descendant named **`Handle`**, welded to `Right Arm`. Without it the katana is cloned into the character but not welded to the arm, and `WeaponAttachment` warns about the missing wield part. The hitbox is a `BasePart` descendant named `Mesh` (for example the blade `MeshPart`) containing `Attachment`s named `Hitpoint`. `Mesh` must be welded to `Handle` (for example with a `WeldConstraint` authored in the template) so it moves with the arm.

Each template must match the weapon definition in `src/shared/weapons/*.lua`.

Keeping templates in `ServerStorage` prevents clients from reading the source models before they are attached to a character.

## World contract

The server registers the `Climbable` collision group during startup.

Climbable surfaces (grab, hang, ledge traversal, corners) **require the `Climbable` CollectionService tag**, on the part or on an ancestor (for example the model). The tag is what makes a surface a climb guide; tagged guides may be invisible, non-collidable query volumes.

The `Climbable` collision group alone does **not** make a part climbable. Parkour queries treat untagged parts in that group as helper geometry and ignore them, and vaults ignore both tagged parts and that group.

## Character contract

The project requires R6. **Set Game Settings > Avatar > Avatar Type to R6 in Studio**; this is a place setting that Rojo cannot set.

Weapon definitions and animations use R6 body-part names (`Right Arm` and `Left Arm`). On any other rig, `CharacterController` rejects the character (the client warns and skips character setup), and the server's `WeaponService` refuses to attach weapons (`WeaponAttachment.IsSupportedRig`) and warns. Without an attached weapon, `CombatService` rejects that player's attacks.

## Source/runtime boundary

Rojo can build the code and vendored package tree directly from this repository. UI and weapon models are deliberate Studio-side authoring contracts rather than missing source dependencies.
